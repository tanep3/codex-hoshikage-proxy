# Gateway修正依頼：生成画像のDiscord自動配信

- 作成日：2026-09-12
- 状態：対応済み（2026-09-13更新）。双方の実装・常駐サービス反映と、利用者によるDiscord画像表示の正常系確認が完了。本文は初期の修正依頼・追加契約案を履歴として保持し、提案値と現行の実装条件を混同しない。
- 対象：codex-hoshikage-gateway／codex-hoshikage-proxy
- Proxy側実装契約：[生成画像API](generated-image-api.ja.md)。以下の提案から具体化した提供条件・制限・旧Responseの扱いは、この実装契約を参照。Gateway側は[生成画像配信仕様](../../codex-hoshikage-gateway/docs/generated-image-delivery-contract.ja.md)を参照。
- 基準：[Workspace / Artifact API v2契約](workspace-artifact-api-v2.ja.md)

以下の第1〜6節は依頼作成時点の記録。現在の確認結果と残る受入項目は[v2受入記録](v2-implementation-status.ja.md)を参照する。

## 1. 解決する問題

Discordで画像作成を依頼した際、生成された画像が回答に添付されない。調査対象の会話では、Codexの保存先にPNGが存在する一方、対応するv2成果物登録とGatewayの成果物配信記録がなかった。

期待する動作は、**画像生成が成功し、配信可能な成果物として保存できたら、依頼元のDiscordスレッドへ自動添付する**こと。利用者に毎回 `/get` を要求しない。文章の回答が空でも画像を配信する。

既存のOpenWebUI PIPE用v1画像取得処理だけでは、v2成果物登録・Discord配信は成立しない。ProxyとGateway双方で以下を対応する。

## 2. 責務分担

| 項目 | Proxy | Gateway |
| --- | --- | --- |
| 画像の発見・帰属 | Codexの出力を検出し、会話・ワーク・Response・Turnとの対応を確定 | ローカルディスクを探索しない |
| 保存・取得 | 不変のv2成果物として保存し、メタデータ・取得・有限リースを提供 | 既存の成果物取得・検証・キャッシュ処理を利用 |
| 登録状況 | 画像の有無、登録進行、失敗・結果不明を永続照会できるようにする | イベント欠落・再起動後も照会して復旧 |
| 配信 | Discordの送信先・添付方法を判断しない | Discord権限、送信先、添付、配信記録、再送判断を担当 |

OpenAI互換の `/v1` は維持する。Gatewayはv2成果物を利用し、v1画像取得API、Codexの保存ディレクトリ、回答中のMarkdownやパス文字列に依存しない。

## 3. Proxy側で必要な対応

1. 生成画像を検出し、該当Responseのv2成果物として自動登録する。モデルによる専用ツール呼び出し忘れで画像が消える構成にしない。
2. 信頼できる実行情報・出力参照から帰属を確定する。共有スレッドの全画像や更新時刻だけで帰属を推測して配信しない。帰属を確定できない場合は結果不明として公開を止める。
3. 既存成果物と同じ不変性、アクセス制御、容量制限、保持期限、リース、ハッシュ検証を適用する。内部保存先の読み取りもパス逸脱・リンク等の検証を通す。
4. 同じ生成出力の再検出・再起動で重複登録しない。専用ツールで既に公開された同一出力も、信頼できる出力識別子で対応を確認できる場合は同じ成果物へ関連付ける。別の生成や別ユーザーの画像をハッシュ一致だけで統合しない。
5. 画像登録の失敗をAI実行失敗と混同せず、元のAI依頼を再実行しない。保存済み回答本文は変更しない。

### 3.1 追加API案：Response単位の画像登録状況

`GET /v2/codex/responses/{response_id}/generated-images`

既存v2と同じ認証・インスタンス・復元世代・会話アクセス制御を適用する。次は提案する応答例。

```json
{
  "response_id": "resp_r1",
  "conversation_id": "conv_c1",
  "workspace_id": "ws_w1",
  "revision": 3,
  "state": "complete",
  "items": [
    {
      "image_id": "img_i1",
      "ordinal": 0,
      "state": "ready",
      "artifact_id": "art_a1",
      "error": null
    }
  ],
  "error": null,
  "expires_at": "2026-09-18T09:00:00Z"
}
```

| 項目 | 意味 |
| --- | --- |
| 全体 `pending` | 出力探索・帰属確認・登録が継続中。現在の一覧だけでは最終件数を判断できない |
| 全体 `complete` | 探索と全項目の登録判断が確定。以後項目を追加しない。全件成功を意味しない |
| 全体 `unknown` | 探索の完了や最終件数を保証できない。空配列でも「画像なし」と扱わない |
| 項目 `creating / ready / failed / unknown` | 画像登録の状況。`ready` のみ成果物IDを使って配信候補にできる |
| `image_id / ordinal` | 再起動でも変わらない画像識別子と表示順。配列の受信順に依存しない |
| `revision` | 同一Response・復元世代内で更新ごとに増える値 |
| `expires_at` | 登録状況の照会保証期限。画像本体の期限は成果物メタデータで確認する |

補足条件：

- `complete` かつ `items: []` のときだけ、画像なしが確定する。
- `complete` では `creating` を残さない。一部登録失敗は各項目のエラーで表す。探索自体の失敗は全体 `unknown` と具体的なエラーで表す。
- `unknown` の再照合で進展した場合はrevisionを更新できるが、元のAI依頼は再実行しない。Gatewayは既に送った項目を再送しない。
- `pending` を無期限に残さず、Proxy側の監視期限を超えたら `unknown` にする。監視期限と照会保持期間の具体値は実装前に運用設定として合意する。
- 項目の `ready` は登録成功の記録。後日の失効・破損・権限取消は、既存成果物メタデータで別途判定する。
- 応答は一貫した全件スナップショットとする。画像件数・応答サイズの上限と、上限超過を明示するエラーを契約に定め、黙って切り捨てない。ページングが必要なら完了判定を含めて契約を追加する。
- 通知は照会を促す手段とし、`artifact.ready` の受信だけを永続的な発見経路にしない。必要なら `response.generated_images_changed` を追加する。
- `response.output_ready` は従来どおり回答保存完了を意味する。画像登録完了の意味を追加しない。
- capabilitiesに対応有無と上限・保持条件を公開する。未対応時は既存の回答配信と `/get` を維持し、画像自動配信を利用可能と表示しない。

このAPIにより、既存成果物一覧のカーソルが後から登録された項目を含まない問題や、空一覧を見て早期に配信完了と判定する問題を避ける。

## 4. Gatewayへの変更依頼

### 4.1 発見・永続化

- Responseごとに画像登録状況を監視し、通知受信、実行終了、回答保存完了、通信復旧、Gateway再起動を契機に照合する。
- 回答配信が完了していても画像監視を終了しない。全体 `complete` と各画像の配信結果を確認して画像配信を確定する。
- `pending / unknown` の照合はバックオフ・期限付きにし、期限後は配信未完了を記録する。画像なし・配信成功に置き換えない。期限後も運用者が再照合できるようにする。
- 依頼元の会話・ワーク・Response・インスタンス・復元世代を検証する。他のチャット、過去Response、共有ワーク全体の画像を自動添付しない。
- 発見済み画像と配信キューへの登録を永続化する。同じインスタンス・復元世代・Response・画像・送信先の組に対し、自動配信を一度だけ起票するDB制約を設ける。

### 4.2 添付と表示

- 既存 `resource_deliveries` の成果物取得・リース・内容検証・Discord添付処理を再利用する。自動発見からこの処理へ接続する。
- テキスト回答と画像配信の状態を独立して記録する。テキストを画像登録待ちで止めない。画像だけの回答も送信する。
- 複数画像は `ordinal` 順を基本とする。後続画像が先に準備できた場合の待機には期限を設け、一部失敗で全画像を止めない。分割送信しても元Responseとの対応が分かるようにする。
- Discordで実際に適用される添付容量・件数制限を用いる。超過時は理由と取得可能性を案内し、配信成功と記録しない。`/get` でも同じ容量制限があり得るため、必ず解決すると案内しない。
- ダウンロード前と送信直前に権限を確認し、安全なファイル名、MIME、サイズ・ハッシュを検証する。認証キー付きURLやサーバー内パスをDiscordへ露出させない。
- 一部失敗時は「回答完了・画像2件中1件配信済み」など、実行と配信を分けて表示する。監視のたびに同じ通知を連投しない。

### 4.3 再起動・再送・停止

- 既存の有限リースと配信復旧を使い、キャッシュ後・送信直前・送信直後の再起動を復旧する。
- Discord送信結果が不明な場合は既存の照合を行い、証拠が不足する間は自動再送しない。AIを再実行しない。
- 明示的な再送は、新しい配信試行IDで同じ成果物を送る。送信結果不明の場合は重複の可能性を利用者に示して確認を得る。自動配信の重複排除と明示再送を区別する。
- `/get` と自動配信の重複も整理する。同じ画像・同じ送信先に既に配信済み、または送信中なら状態を案内し、再添付は明示操作にする。別の送信先への明示取得は権限確認を通す。
- `/stop` は従来の実行停止として扱う。停止までに登録成功した画像は、停止された実行の途中成果であると分かる形で配信する案とする。配信取消機能が必要なら実行停止とは別契約にする。
- 正式復元による世代不一致は既存契約どおり照合を先行する。世代変更を理由に古い配信を新規起票し直さない。

## 5. 受入条件

| ケース | 確認する結果 |
| --- | --- |
| 画像1枚、文章のみ、画像のみ | 自動添付または画像なし確定が正しく、不要な空投稿がない |
| 画像複数、一部登録失敗 | 表示順と画像ごとの結果が分かり、成功分を配信できる |
| 回答保存完了後に画像登録 | 回答配信後でも画像を発見・配信する |
| 回答保存失敗、画像登録成功 | 画像は独立して配信でき、AIを再実行しない |
| 停止・実行失敗と画像生成の競合 | 登録済み画像と途中成果の表示が契約どおりになる |
| 通知欠落・重複・通信切断 | 状態照会で回復し、同じ画像を自動重複送信しない |
| 発見直後・キュー登録中の再起動 | 配信漏れも重複起票もない |
| Discord送信直後に応答喪失 | 結果不明を成功扱いせず、証拠なしで再送しない |
| `/get` と自動配信の競合、明示再送 | 重複抑止と利用者による再添付を区別する |
| 別会話・過去Response・共有ワーク | 対象外画像を配信しない |
| 期限切れ・権限取消・破損・容量超過 | 配信しない理由が保存・表示される |
| 登録状況がunknown、探索上限超過 | 画像なし・全件成功と偽らず、有限監視後も再照合可能 |
| Proxy/Gateway再起動・正式復元 | 世代照合、既存配信記録、リースが整合する |

単体・結合試験に加え、実Codexで画像生成から不変成果物取得まで確認する。Discordへの実送信は許可されたテスト先で確認し、モック送信成功だけで表示確認済みとしない。反復する試験は新規依頼のIDを一意にし、再起動試験では同じ永続IDを引き継ぐ。

## 6. Gateway側に確認してほしい点

1. 既存 `resource_deliveries` を使った自動配信、回答と画像の独立した状態管理、DBの重複抑止がこの分担で実現できるか。
2. 追加API案に必要なフィールドの不足がないか。監視期限、照会保持期間、件数・サイズ上限、再起動後の再照合方法をProxy側と確定する。
3. 複数画像の待機・分割表示、途中成果の配信、`/get` 競合・明示再送のUXに修正希望があるか。

依頼時点では、合意後にProxyのAPI契約と双方の要件・設計・DB・受入試験を更新し、実装する方針だった。現在は冒頭に記したとおり対応済み。第5節の受入条件一覧そのものは、全項目の実環境試験が完了したことを意味しない。
