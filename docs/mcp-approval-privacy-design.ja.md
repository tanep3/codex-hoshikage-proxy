# MCP承認で誰に内容を見せるか — 判定仕様

2026-09-17。0.5の詳細設計。未実装・未受入。対象は承認前の実引数であり、ツールが実行後に返す結果の配信制御とは別である。

普通の検索語・URL・非機密の文章は元の会話に表示する。個人情報・連絡先・DM／メール・認証情報・実行コードを含むときは、「自分だけに表示して確認」から**依頼した本人だけが見られるメッセージ**で確認する。押した人が依頼者でなければ内容を返さない。開いただけでは操作を実行しない。

## 1. 判定の順序と結果

1. 評価済みの接続・ツール・定義と実引数を照合する。照合不能を「個人情報だから」と説明しない。
2. ツール別に、呼出し全体が個人的なやり取りか、個人情報・認証・実行コード用のフィールドを含むかを判定する。
3. 表示する全文字列を下記の規則で検査する。配列・objectの内側、URLのpath/query/fragmentも対象とする。表示から外すプロトコル値は評価済みの役割に限定する。
4. いずれかの値が本人向けなら呼出し全体を本人向けにする。機密部分だけ伏せて他の本文を公開しない。
5. 表示内容の完全性と、今回だけ許可／依頼中許可の適格性を別々に判定する。本人向け表示になったことだけを理由に全て単発へ変更しない。

内部の判定はpublic / requester / unclassified。unclassifiedは本人向けに扱い、診断はprivacy_unclassified。内容を安全かつ完全に説明できない場合は、本人向けにすれば許可可能になるとは扱わない。制御文字等で表示不能ならinformation_incomplete、未知引数ならunknown_argumentsを優先する。

複数理由がある場合の公開診断はauthentication_information、executable_code、private_communication、personal_information、privacy_unclassifiedの順とする。ログに検出値・一致部分・秘密の無鍵ハッシュを残さない。

## 2. 検査用の正規化

元の実引数は変更しない。表示とcall照合は原文を拘束し、検査用の派生文字列だけを作る。

- JSONのescapeはJSONパーサーによる復元後に検査する。文字列を勝手に別のJSON構造へ変換して操作を解釈しない。
- 元文字列に加えUnicode NFKC正規化した文字列も検査する。全角の英数・記号による既知形式の見落としを防ぐ。
- 正しいpercent encodingを持つ文字列は最大4段階まで復号して検査する。URL queryの`+`は空白として扱う検査も行う。復号後は改めてNFKC検査する。
- 4段階後も復号で内容が変わる、復号結果が不正UTF-8になる、既知の符号化フィールドを解釈できない場合はunclassified。普通の文章の単独`%`まで符号化異常にしない。
- MIME、base64、SQL、内包コマンドは汎用文字列の推測復号をしない。評価済みの専用規則で解釈する。メールは復号できるかに関係なく全体を本人向けにする。
- 検査の上限は1呼出しの文字列合計256KiB、派生文字列合計2MiB、構造深さ64。超過時は検査未完了としてunclassified。表示自体の上限超過は別途information_incompleteとし、検査を途中で止めた値を公開しない。
- NUL、改行・タブ以外のC0制御、DEL、双方向表示の上書き／分離制御は公開・本人向けともそのまま描画しない。意味を確定した可視表現を作れなければ許可不可。通常の改行・タブは表示契約に従って可視化する。

## 3. 検出規則

以下は最低限の決定的な検査規則。ツール別のフィールド分類と併用し、これだけで全ての個人情報を識別できるとは保証しない。

| ID | 条件 | 判定 |
| --- | --- | --- |
| PR01 | Gmail全操作、個人宛てのNotion session、家族設定・trusted contactの評価済み操作 | requester。個人的なやり取り／個人情報 |
| PR02 | 評価済みの宛先・連絡先・氏名・個人ID・参加者フィールドに値がある | requester。空配列／null／未指定を、存在しない個人情報と区別する |
| PR03 | ASCII local-part、`@`、ドットを含むDNS名のメール形式。local-partは英数と`.!#$%&'*+/=?^_`{|}~-`、DNS labelは英数・hyphen | requester。URL中・本文中も対象。`@all`だけはメールとしない |
| PR04 | `+`で始まる国番号付きの8〜15桁、または日本の国内番号として区切られた10〜11桁（先頭0、3〜5桁／1〜4桁／4桁の3群） | requester。空白・hyphen・丸括弧の区切りを許容。日付・小数・版番号を単なる数字連結で電話にしない |
| PR05 | `電話`／`電話番号`／`tel`／`phone`ラベルとコロン・等号を挟んだ7〜15桁の値 | requester。区切りなし電話にも適用 |
| PR06 | `住所`／`address`、`氏名`／`full_name`、`個人番号`／`マイナンバー`等の識別ラベルとコロン・等号に続く非空の値 | requester。一般語の出現だけでは判定しない。ラベル照合はASCII case-insensitive、空白を許容 |
| PR07 | 郵便番号（3桁-hyphen-4桁）と、都道府県／市区町村・番地を含む同じ値、または評価済み住所フィールド | requester。`東京都の天気`だけを住所と判定しない |
| PR08 | AuthorizationのBearer/Basic値、Cookie/Set-Cookieの値、password/passwd/api_key/access_token/refresh_token/client_secret等の評価済み秘密キー・代入ラベルの非空値 | requester。秘密入力の作用は常に単発。単に「APIキーの設定方法」という説明文は該当しない |
| PR09 | URLのuserinfo、queryキーtoken/access_token/api_key/key/signature/sig/code、AWS/Google署名用キー（ASCII case-insensitive）に値がある | requester。`key`等は保守的判定。公開用の無関係な値も該当し得る限界を記録する |
| PR10 | private key PEM開始行、3区画のbase64urlでheaderがJWTのJSON objectとして識別できる値 | requester。JWT署名の真正性検証や認証試行はしない |
| PR11 | 評価済みの任意実行コード、Cookie/storage復元、認証用フォーム、資格・環境変数の設定 | requester。任意コード・秘密入力・認証は単発 |

PR04の数字桁数は区切りを除いた数。PR05〜08の本文ラベルは行頭、空白、引用符、object区切りの後を境界とし、コロンまたは等号から同じ行の値を検査する。objectのキー／値は構造として検査する。URL queryはデコード済みのキーと値で判定する。電話や住所を探すために離れた項目を結合しない。

未知の自由文に含まれる人名や独自の秘密番号は完全には識別できない。既知の入力目的・フィールドは先に本人向けにし、意味を評価できない構造はunclassifiedにする。通常の自由文を全てunclassifiedにすることも、検出できなかったから機密でないと保証することも禁止する。判定範囲とこの限界を利用者向けマニュアルにも記載する。

## 4. 具体的な受入データ

[判定例JSON](mcp-approval/privacy-cases.json)を設計時の期待値とする。架空の連絡先・テスト用値だけを使用する。各caseのexpectedは公開範囲であり、依頼中許可の可否ではない。これらの作成は実装のテスト合格を意味しない。

実装後は初回表示・承認時の再検証・後続の自動適用の全てで同じ規則を通す。各規則の肯定例と、通常の検索語・URL・編集文・日付等の否定例を検査する。Gatewayでは依頼者以外の押下、元会話と別会話、古いカード、本文をログ／DB／公開エラーへ流出させないことも別に試験する。

## 5. 実装前に残る対応付け

342ツールの全フィールドへ本規則の具体ID・表示ラベルを割り当てる。動的な内包操作とMIME等は専用規則の意味評価を完了する。台帳の未評価行に本書へのリンクを付けただけでは完了としない。自然文の個人情報の完全識別ができる、と要件や試験の合格記録へ書かない。
