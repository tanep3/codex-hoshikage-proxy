## 原則と今回の是正

MCPターン許可では、契約書の補完とコーディングを並行して進めてしまった。文書の完成を実装開始条件として確認しなかったことが原因である。先行コードを正本にして仕様を追認せず、文書を先に完成させる。先行コードは未完了として保持し、開始条件が満たされるまで追加実装を停止する。配備は別の条件で判定する。

## 開始条件

| 工程 | 開始条件 | 完了時に残す証拠 |
| --- | --- | --- |
| 要件・設計 | 依頼と既存契約を確認 | 責務、要件、制約、未確定事項 |
| 必要な実証 | 文書へ実証目的・範囲・合格条件を記載 | 観測事実、限界、仕様への影響。製品実装と区別 |
| 具体契約完成 | API、全状態、競合、エラー、保持・上限、互換性、受入を記載 | 文書間の整合確認、レビュー指摘対応表、完成版パス |
| 実装 | 上記文書が完成・提示済み、接続上の指摘が解消済み | 基準とした契約版、要件と実装の対応 |
| 受入 | 基準版に沿う実装が完成 | 受入IDごとの結果と証拠、未検証事項 |
| 配備 | 受入条件を満たし、配備の承認範囲を確認 | 対象版と配備後確認 |

文書の「完成」、双方の「合意」、コードの「実装済み」、試験の「受入済み」、サービスの「反映済み」を別々に記録する。未検証事項は受入条件・合格基準が具体化されていれば文書に残せるが、API形式や責務の未決定を「後で実装しながら決める」として実装開始しない。

## 変更要求が来た場合

1. 影響するコーディングを止め、要件・設計・契約・受入条件へ先に差分を反映する。
2. 既存仕様との矛盾と対向システムへの影響を確認し、指摘ごとの回答を記録する。
3. 改訂版を提示し、対向接続上の指摘が解消してから実装を再開する。既存の合意や承認を無意味に取り直すことはしない。
4. 途中報告には現在の工程と未完了事項を明記する。文書を更新した事実だけで「仕様確定」と報告しない。

この手順の例外を担当者の判断で設けない。ユーザーが順序変更を明示した場合だけ、その指示と適用範囲を記録する。
