# MCP承認 — Notionの複合操作の詳細設計

> 2026-09-17 適用範囲確定：本書の部分置換禁止は、該当ポリシーを明示指定した実行だけに適用する。未選択実行を含むProxy全体の既定禁止ではない。[責務再整理](mcp-approval-layering-revision.ja.md)を参照。

2026-09-17。0.5の内部詳細設計。製品コード・常駐への反映前。接続APIは変更しない。

## 1. 今回確認した根拠と台帳の不足

隔離取得した実カタログの定義に加え、提供元のNotion fetchから`notion://docs/view-dsl-spec`と`notion://docs/enhanced-markdown-spec`を読んだ。利用者のページ・DB・メールは取得していない。データ更新ツールは実行していない。

設計台帳で単なるwrite候補だった操作に、次の作用分岐がある。

- create/update-viewのFORM設定は、投稿の受付・匿名投稿・投稿者の権限を変える。通常の並び順変更と同じ許可で適用しない。
- 本文中のpageタグや既存databaseのurlは、単なるリンクではなく既存ページ・DBの移動を指示できる。mention-page/databaseとの違いを表示する。
- synced_block_referenceの子内容を変更すると、元の同期ブロックにも反映される。表示中のページだけが変更対象だと説明しない。
- update-pageのallow_deleting_content=trueは、参照から外れた子ページ・DBの削除を許可する。通常の文章の置換と分ける。

これは設計候補の不足を検出した記録であり、常駐で誤った自動許可が適用された証拠ではない。ツール名だけで作用を固定せず、実引数の構文から判定する。

## 2. view設定の解析と表示（notion_view_configuration）

対象はnotion-create-view.configureとnotion-update-view.configure。元の文字列を変更せず、表示用に文法解析する。引用符内のセミコロン・改行を命令区切りとして扱わない。ASCII keywordは大文字小文字を区別せず、属性名・値の大小は保持する。入力全体を消費し、末尾の未解釈部分を捨てない。未評価の構文はoperation_semantics_unverified。

| 命令 | 表示内容 | 作用・条件 |
| --- | --- | --- |
| FILTER | 対象属性、演算子、全値、括弧を保持した条件式 | write。AND＝すべて、OR＝いずれか。複数FILTERはAND。個人属性・値は本人向け |
| SORT BY | 属性ごとの優先順と昇順／降順 | write。方向省略は昇順と明示 |
| GROUP BY | グループ化する属性 | write。boardで必須という条件も検証 |
| CALENDAR BY | カレンダーの日付属性 | write。calendarで必須 |
| TIMELINE BY | 開始属性、終了属性の有無 | write。終了指定なしを勝手に別属性へ補完しない |
| MAP BY | 地図の位置属性 | write。実際の住所等が入力される場合は本人向け |
| SHOW / HIDE | 表示／非表示にする属性の全件と順序 | write。項目を非表示にすることとアクセス権の削除を混同しない |
| COVER | 表紙用属性、指定したサイズ・収まり方 | write。省略したサイズの上流既定は未確認なら「指定なし」 |
| WRAP CELLS | セル内で折り返す／折り返さない | write。booleanをそのまま表示 |
| FREEZE COLUMNS | 固定列数 | write。整数、負数不可 |
| CHART | 図の種類、集計、対象属性、色、高さ、並び、積上げ、説明文 | write。提供元が明記したenumだけを評価。集計省略は件数。未記載の集計関数を推測しない |
| FORM OPEN / CLOSE | フォームの回答受付を開始／終了 | permission_change、毎回確認 |
| FORM ANONYMOUS | 匿名回答を許可／不許可 | permission_change、毎回確認 |
| FORM PERMISSIONS | 回答者に与える権限 | permission_change、毎回確認 |
| CLEAR FILTER / SORT / GROUP BY | 既存の絞込み／並び順／グループ化の解除 | write。データ本体を削除する操作とは区別。update-view専用 |

FORM PERMISSIONSの値はnone/comment_only/reader/read_and_write/editor。「権限なし／コメントのみ／閲覧／読み書き／編集者」と原enumを併記する。各役割の細かな権限をProxyが追加推定しない。ツールの短い説明では省略されていた2値も、提供元DSL仕様で確認した。

FILTERの比較は`= != > < >= <=`、文字列条件はCONTAINS/STARTS WITH/ENDS WITH、空値はIS EMPTY/IS NOT EMPTY、集合はIN。AND/ORと括弧を表示する。relation/person等では同じ`=`が包含の意味になり得るため、対象の属性型を確認せず数値の等号と同じ日本語へ変換しない。person系は本人向け。属性型に依存する解釈の根拠を取得・拘束する方法は第6節の残課題に含む。

一つのconfigureに通常設定とFORMが混在したら、呼出し全体にpermission_changeを含めて毎回確認する。許可済みのSORTを先に実行してFORMだけ止める分割実行はしない。Proxyは上流の1callを勝手に分割しない。

## 3. 本文・置換（notion_content_updates / notion_markdown_effects）

content_updatesは表示上の配列順に、old_str/new_str/replace_all_matchesを「検索する本文／置換後の本文／一致箇所をすべて置換」に対応付ける。old_strは非空。最大100組。replace_all_matches省略はfalse（複数一致なら上流がエラー）と明示し、1件に勝手に選ぶ処理をしない。未知キーを読み飛ばさない。置換対象の実データを取得していないのに、一致箇所や変更件数を断定しない。

通常の文章の修正と確認できた場合はwrite。new_strだけを見てこの条件を満たしたと判定しない。文章内の文字を減らすこと全てを、利用者が毎回確認としたリソース削除へ機械的に分類しない。一方、子ページ・DBを削除可能にする指定はdeleteで単発。allow_deleting_content=false／省略では上流が拒否する削除を、Proxyが許可したとは表示しない。

本文は全文を表示し、MarkdownをDiscordで実行・展開しない。タグ・リンク・メンションも可視の文字列と固定説明として表示し、ユーザーへの通知やURLの自動アクセスを起こさない。

| 本文の構文 | 確認すべき対象と作用 |
| --- | --- |
| 通常の文章・見出し・装飾・コードブロック | write。保存するコードと実行するコードを区別する |
| mention-user / mention-agent | 対象IDと全文を本人向け表示。通知等の外部作用の確定までは単発 |
| mention-page / mention-database | リンク先の参照。page/databaseブロックの移動とは区別する |
| page url / database url | 既存リソースの移動。移動元・先の実効権限変化を確認できない場合はpermission_changeとして単発 |
| database data-source-url | 既存データソースのリンクビュー作成。対象IDと挿入先を表示。元データを移動する操作とは区別 |
| synced_block_reference＋子内容 | 同期元と参照先に及ぶ変更を明示。対象範囲の根拠がなければ依頼中許可を適用しない |
| file/image/audio/video/pdf/embedのsource | 添付・取込元を全て表示。署名URL等は本人向け。取得・共有・既存資源変更の作用を専用規則で確認する |
| meeting-notesのtranscript | 編集不可という提供元仕様を明示。書換えを通常編集として承認しない |

引用・escape・コードブロック内の文字を、実際に解釈されるタグと混同しない。逆に正規表現でタグっぽい文字を消しただけで通常文章と判断しない。特別構文の解析が不足した状態を「本人向けなら通常編集として許可可」にしない。

### 3.1 将来、部分置換を許可対象に広げるための条件

Gatewayの追加指摘を受け、以下を将来の許可対象拡張の必須条件とする。現版は第3.2節の実行不可を優先する。タグ内のURLだけの変更、複数置換による構文の合成、コード囲みの除去、同期ブロック内の変更は、new_str単体の検査では判別できない。上流がどの範囲を再解釈するかは未実証であり、実害を確認済みとはしない。

1. **対象の確定**：承認callと同じ認証接続・workspace・page IDの、欠落のない編集対象を取得する。モデルが引用した本文や要約は根拠にしない。部分取得・省略・読取権限不足を完全な本文として扱わない。
2. **編集意味の確認**：上流が配列を順番に適用するのか元本文へ一括適用するのか、一致の数え方、重複範囲、escape、正規化、エラー時の部分適用の有無を確認する。表示順序が配列順であることを、上流の逐次適用の証明にしない。
3. **結果の評価**：確認した上流の意味に従って全置換を評価し、変更前後の構造・作用・対象を比較する。上流が途中ごとに反映／再解釈するなら中間状態も全て評価する。最終結果だけが通常本文でも、中間の移動・削除を見落とさない。文字列単位の独立判定結果を足し合わせるだけでは不十分。
4. **対応付け**：対象の識別子、接続世代、内容の版、完全取得の証拠、実引数全体と順序、評価規則の世代を内部の評価根拠へ拘束する。内容は有界メモリのみ、外部へ出す照合値はプロセス鍵付きの不透明値。既存scopeに文書内容を公開追加しない。
5. **更新競合**：取得後に本文が変わり得る。承認直前に読み直すだけで実行時の一致を保証したとは扱わない。上流の条件付き更新、または実行まで有効な排他等の実効的な保証が必要。Proxy内のロックはNotionの他利用者による編集を防がない。導入ツールがその保証を提供するかは未確認。
6. **表示**：置換する文字列だけでなく、構造上の位置、移動先／同期先等の変更対象、複数一致への適用範囲を説明する。取得した既存本文の秘密・個人情報にも公開範囲の検査を適用する。既存本文を取得できたことを、その全文の公開許可と扱わない。

対象版が変わった場合は旧表示・旧評価根拠を使用せず、再評価する。同じツールの既存grantがあっても、後続callの対象本文・版を別途確認する。本文変更を検出できないままTTLだけで安全とする設計は採用しない。

### 3.2 単発確認と実行内容不明の区別

| 根拠と評価 | 扱い |
| --- | --- |
| 対象本文・上流の置換意味・実行時の版対応を確認でき、全適用状態が通常編集 | 既存policyの他条件も満たす場合だけ依頼中許可可能 |
| 同じ根拠で移動・権限変更・削除等を確認し、全作用・対象を完全に説明できる | 説明を表示して今回だけ許可。自動適用しない |
| 対象本文が不完全、適用順序が不明、解析不能、版との対応を保証できず実作用が変わり得る | operation_semantics_unverifiedまたはinformation_incomplete。許可不可。本人向け表示や単発ボタンだけで不足を埋めない |
| 上流が状態非依存の制限付き編集を保証し、取り得る全状態で作用・対象を確定できる | その保証を個別に評価して分類。一般の文字列置換に根拠なく適用しない |

2026-09-17の利用者決定により、**変更対象を保証できない部分置換は実行しない**ことを製品仕様として確定した。これは未実装を機密例外へ付け替える措置ではなく、上流の保証範囲に基づく明示的な制限である。本人向けへ移しても単発許可を出さない。他の編集方法へ勝手に変換して実行しない。

現在の導入定義と利用可能なtool declarationには、notion-update-pageへ期待する本文版を渡す定義済み項目がない。additionalPropertiesが許容する任意キーを、上流が解釈する版一致条件だと推測しない。提供元の排他等も確認できていないため、現版のcommand=update_contentはoperation_semantics_unverified、state=unavailable、allow_once=false、allow_turn_tool=falseを返す。依頼中許可にこの分岐を含めない。

利用者への説明は「確認した本文と、実行時の本文が同じだと保証できないため、この部分置換は実行できません」。拒否・/stopの既存経路を維持する。APIへ新reasonは追加しない。単にコード未実装という説明にも、本人限定なら実行できるという説明にもしない。

この制限下での部分置換経路の設計は確定。将来この機能を許可対象へ広げる場合に限り、上流の置換順序・中間作用・完全読取・実行時版対応を再評価し、policy世代を変更する。これら未確認の意味を仮定して現版の実装開始を待ち続ける設計にはしない。他のcommandの意味・表示設計が完成したという意味でもない。

判定順序は、call対応・定義照合、入力schemaと評価済みキーの検証、command別の実行可否、表示／許可範囲の順とする。空のold_str（NP08）と未評価キー（NP09）はunknown_arguments、それ以外の検証済みupdate_contentはoperation_semantics_unverified。どちらも有効な許可tokenを発行しない。理由表示へ本文や個人情報を埋め込まない。

初回表示だけでなく、手動返信の確定時と既存grantの後続適用でも同じ実行可否を検証する。以前の通常編集grant、本人向け表示、管理者の許可対象設定で上書きできない。古い表示や他profileへの切替を迂回経路にしない。承認待ちの間も実行しないことを、上流への許可返信数と実更新数で受入確認する。上流が承認を要求せず実行する設定については、Proxyの表示制御だけで実行禁止を保証できないため、その経路を含む制御点の確認を実装設計・受入の必須項目とする。

| ID | 現版の受入条件（未実行） |
| --- | --- |
| NR-01 | 正常形式のupdate_contentは元会話・本人向けとも許可不可、固定理由、tokenなし |
| NR-02 | NP08／NP09はunknown_arguments。入力不正を版保証不足へ誤分類しない |
| NR-03 | 既存grant／明示許可設定があっても上流への許可返信0回、本文更新0回 |
| NR-04 | 古いカード・直接単発reply・旧profileへの変更で制限を回避できない |
| NR-05 | 拒否・停止は利用可能。別commandの代行実行・AI依頼の再送は0回 |
| NR-06 | 再起動・復元・定義変更後も、将来の再評価なしに許可へ復帰しない |

## 4. 許可範囲の再評価

通常設定のturn_tool grantがあっても、後続のFORMや移動・削除を自動適用しない。毎回configure・本文・全optionを解析し、呼出し全体の作用集合を合成する。policy_generationはこれらの判定規則も含む。通常設定用の許可を作るカードには、権限変更・リソース移動の未確認作用・削除等は毎回確認になることを表示する。

公開可否は独立に判定する。FORM PERMISSIONS readerのような値そのものが個人情報でない操作は元会話で全文表示して単発許可できる。反対にread条件でもpersonフィールドを含めば本人向け。

## 5. 受入例

[設計時の期待値](mcp-approval/notion-operation-cases.json)を使用する。ツールを実行した結果ではない。通常操作からFORMへ変わる場合、両者の混在、引用符・大小文字・未知命令、ページ移動とリンク、削除指定、検索置換の範囲を別々に検証する。実装後は初回と後続自動適用に同じ判定器を通す。既存NP01〜NP07は意味評価用の条件付き期待値を保持するが、現版でupdate_contentを許可する期待値は撤回し、別のrelease_expectedを正本にする。評価根拠を実際に取得できたという結果ではない。追加の文脈依存例は[部分置換の期待値](mcp-approval/notion-replacement-context-cases.json)を参照する。

## 6. この設計群に残る具体作業

- データソースの属性型に依存するFILTER／propertiesの解釈について、実行先と同じ接続・対象のschemaを取得し、承認callへ拘束する経路を確定する。モデルの説明から属性型を補完しない。
- 全DSL構文の字句・escape・型条件と、Markdown特別構文の完全な文法・未対応診断を確定する。上の表だけで全入力の評価を完了とはしない。
- propertiesのnullについて、導入定義の概要は「非null値で更新」、フィールド説明は「nullで削除」と記している。概要だけでnullを無視せず、提供元の意味または隔離した専用データで確認してから確定する。
- 添付・同期ブロック・ページ移動等の追加対象を、漏れなく説明する具体表示と試験値を完成させる。
- 第3.1節の対象本文読取・順序・競合保証は、現版では第3.2節の利用者決定による実行不可で閉じる。将来対応の前提として記録を保持し、現版の実装ゲートからは外す。Gatewayへ本文の意味評価を移管しない。

これらは内部詳細設計の残作業であり、Gateway合意済みの0.5接続形式の差し戻しではない。完成前に製品コードへ入らない。

第3.2節の承認通知を通らない経路について、[実行制御設計](mcp-approval-execution-boundary.ja.md)を追加した。導入版のソースでprompt、承認記憶、reviewerと設定優先順位を確認し、対象ツールをProxy検査へ通す方法を具体化した。NR-07は設計方法未定から実機受入待ちへ進める。上流版・管理設定・モデルによる条件が合わない場合に新規実行を始めない設計を維持する。
