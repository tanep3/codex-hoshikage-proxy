# MCP承認 — 汎用基盤とポリシー拡張の責務再整理

2026-09-17。利用者・Gatewayからの指摘に基づく設計改訂。方向性を本書に整理する。利用者からGatewayの合意を受領済み。0.5の既存wire契約を黙って変更するものではなく、接続差分の確定・レビュー後に後継契約へ反映する。製品コード・常駐環境は未変更。

## 1. 是正する設計上の問題

従来の是正設計では、操作内容の表示、個別承認の仲介、依頼中許可の意味評価、実行禁止を同じ完成条件に束ねていた。そのため、342ツールの完全解析が汎用の承認表示まで止め、Notion禁止規則を標準APIにも波及させる記述が生じた。これを是正する。

| 層 | 保証する責務 | 担当しないこと |
| --- | --- | --- |
| Proxy中核 | Codex実行、実callと引数の忠実な取得、承認要求・返信の対応、単発承認、停止、状態照会、永続化・冪等性・復旧 | 全ツールの安全性評価、Discordの投稿やボタン |
| 汎用表示機能 | 構造と値を欠落させない表示データ、公開可否、分割・完全性の証明、評価済みの説明があれば補助表示 | 任意のツールの意味を理解済みと偽ること、表示の未評価を実行禁止へ変換すること |
| 汎用承認ポリシー拡張 | 明示選択した範囲の依頼中許可、適用・失効、明示的な実行禁止、上流設定の必要な制約 | Gatewayを名指しした分岐、未選択の実行への規則適用 |
| クライアント | 利用者認証、表示先の認可、具体的UI、配信確定、ボタン操作、クライアント再起動復旧 | 実callの推測、欠落した内容への許可、Proxyのgrant条件の迂回 |

Gatewayはこのクライアントの一実装。OpenWebUI、Web、CLIなども同じ承認・表示・ポリシー契約を選択できる。Proxyの中核はDiscord IDやボタン文言に依存せず、認証された主体・会話・実行IDを扱う。clientから来た任意のuser_idを認証済みとみなさない。

## 2. 表示できることと自動許可できることを独立させる

中核の単発承認には、信頼できる上流承認要求、安定call対応、全実引数、不変の確認対象、返信先、現在の実行状態が必要。未評価のツールであることだけを理由に単発承認を止めない。

汎用表示は操作名、サーバー、実引数のキー・型・構造・値全体を示す。説明辞書がなければ上流の識別名も併記し、未知キーを削らない。null、未指定、空文字、空配列、数値、配列順、入れ子を区別する。任意コード・HTML・メンションを表示時に実行しない。上流descriptionは説明資料であり、安全性や正当性を保証するものではないと区別する。

評価済みの表示アダプタがある場合は日本語の意味説明を追加できるが、原引数を置き換えて別操作を表示しない。アダプタの未対応・定義の変化だけで汎用表示を失わせない。引数の完全取得やcall対応ができない場合は単発承認も不可。サイズ上限で欠落した値を省略表示したまま許可しない。

公開範囲の保証は維持する。公開してよいと判定できないデータは依頼した本人だけに表示する。意味解析未対応と個人情報検出は別の理由として示す。私的な表示は「安全性評価済み」を意味しない。通常の非機密入力については評価済み公開ルールを使い、汎用経路の存在を理由に全て本人向けへ戻さない。

| 状況 | 単発承認 | 依頼中許可 |
| --- | --- | --- |
| 実call・全引数・表示の完全性を確認、意味未評価 | 上流が求めた単発承認を仲介 | 不可。未評価と明示 |
| 評価済み通常操作、適用中ポリシーの条件内 | 可 | 利用者が明示選択した場合のみ可 |
| 評価済みだが外部送信等の毎回確認対象 | 可 | 不可 |
| 適用中の明示ポリシーが実行禁止 | 不可 | 不可 |
| call対応・全引数・表示の完全性が不足 | 不可 | 不可 |
| 上流が承認を要求していない | 中核が独自の承認を追加しない | ポリシーが上流へ確認を強制する範囲は明示する |

## 3. 拡張の選択と実行境界

表示profile、ポリシー選択、依頼中許可の作成は別の選択にする。表示機能を要求しただけで実行禁止を有効にしない。機能が利用可能というcapabilityも選択とは区別する。

ポリシーはサーバー登録済みの識別子・版で選び、クライアントが任意の評価コードを渡す方式にしない。実行受付時に適用するポリシーと実効世代を確定・永続化し、要求の冪等照合へ含める。未知ポリシーを無視して実行を開始しない。サーバーが当該クライアントへ強制する規則がある場合は、その規則も適用結果に明示し、省略で外せない。

適用中の実行では、旧画面・別表示profile・直接reply・grant経路から禁止を迂回させない。停止・Steer・終了・失効の境界は既存合意を維持する。次Runのポリシー選択と、前Runの許可の持越しを混同しない。

上流確認を強制する設定を共有runtimeへ一律に書くと、非選択クライアントへ影響する。runtimeとThreadの再利用可否を実効ポリシー・承認設定の互換性で分け、非互換なら設定を相互に上書きして使い回さない。設定反映完了前にTurnを始めない。同じ会話でポリシーを変更する場合も、会話継続の保証と上流設定の適用方法を具体契約で確定する。黙って別会話を作らない。

## 4. Notion部分置換の決定を維持する

「保証できない部分置換は実行しない」という利用者決定は撤回しない。利用者は2026-09-17、禁止の適用範囲を「ポリシーを指定した実行だけ」と決定した。全実行へ展開しない。

確定方針は当該ポリシーを明示適用した実行に限定する方式。Gatewayはそのポリシーを選び、他クライアントは未選択ならCodex既定の単発承認経路を使う。これは未選択の操作の安全性をProxyが保証する意味ではない。選択した実行に対する上流制御は[実行制御設計](mcp-approval-execution-boundary.ja.md)の技術的知見を再利用する。

## 5. 文書と実装の工程

「文書完成後にコード」の順序は維持する。一方、保証の異なる全342ツールの意味評価を一つの巨大な着手条件にしない。

1. 中核の汎用承認・完全表示・取得障害・ページ・認可・復旧を一つの製品機能として詳細設計し、接続差分を合意する。
2. ポリシー拡張の選択・適用範囲・実効設定・runtime分離・失効を詳細設計する。
3. 初期ポリシーの評価済み範囲を全件台帳で明示する。未評価も汎用の単発承認で扱い、依頼中許可は提供しない。
4. 各機能の要件・設計・受入条件が完成した後に、その機能を実装する。既存3形式だけを直して全MCP対応完成とはしない。
5. 実ツール・実クライアントとの結合受入、配備・運用説明を経て完成とする。

342件の台帳・詳細調査は、評価済みポリシーを拡充する資料として残す。未評価を自動許可へ入れたり、逆に単発承認を全面停止させたりする用途にはしない。

## 6. 後継API契約で確定する差分

- 汎用表示と評価済み説明の区別。安全性評価の有無と単発承認可能性を別々に返す。
- ポリシー選択と適用結果の要求・応答、世代、capability、冪等性、未知値のエラー。
- ポリシー未選択時のscopeと単発reply。未取得のpolicy世代を捏造しない。
- 既存0.5の意味未評価unavailable、renderer enum、必須tool_policy等との差分。旧契約の意味を無告知で変えない。
- 非公開表示・全ページ照合・利用者認可・停止・復旧は引き続き必須。

## 7. 追加受入

LR-01：未評価ツールでも実引数を欠落なく確認し、上流の単発承認を仲介できる。依頼中許可は出ない。
LR-02：公開可否が未確認なら本人向け。未知キーは原引数に残り、意味評価未対応を秘密検出と偽らない。
LR-03：同時実行する別クライアント・別ポリシー間で上流設定、grant、call、表示を共有しない。
LR-04：選択中ポリシーの禁止を古い画面・単発replyで迂回できず、未選択実行へは禁止が暗黙適用されない。
LR-05：policy未対応・設定結果不明・runtime非互換時は、ポリシーを落として実行しない。
LR-06：カタログ取得不良と意味評価未対応を区別。完全なcall根拠がない場合には許可しない。
LR-07：同一の中核APIをDiscord固有情報なしのクライアントでも使える。Discord配信失敗をCodex実行失敗に変換しない。

後継の具体契約は[API 0.6レビュー案](mcp-approval-api-v06.ja.md)。責務整理の合意と、この具体契約の接続レビュー完了は区別する。
