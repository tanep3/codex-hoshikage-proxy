# 操作の意味に基づく依頼中承認委任：Proxyレビュー

## 0. 最上位目的と初期リリースの境界

**最上位目的：既存の個別確認・禁止規則を維持しながら、同一依頼中に利用者が同種の承認操作を繰り返す必要をなくす。** ボタンの回数だけでなく、操作完了までの待ち時間も減らす。汎用的な意味解析基盤を完成させること自体を目的にしない。

回答0.1は最終的な拡張可能性と初期リリースの成立条件を十分に分けていなかった。以下の範囲分けを推奨する。小さいプロトタイプではなく、**対象範囲を明示した、運用可能な製品機能**として完成させる。

| 区分 | 初期リリースに含める | 後から広げられる範囲 |
| --- | --- | --- |
| 委任境界 | 1依頼の1実行・入力世代、明示したMCP接続先と有限のツール群 | 複数接続先をまたぐ委任 |
| 操作群 | 実際の連続作業で承認が繰り返されている操作から選び、証拠を取れる範囲を明記 | 別の操作群・別のadapter |
| 判断 | 固定規則→機械的照合→必要な場合だけ独立LLM判定 | 新しい機械判定ルール・追加の意味判断範囲 |
| 品質・運用 | 対応付け、対象証拠、必要な対象拘束、停止・取消、再起動、永続監査、上限、UI、実環境受入 | これらの必須保証は後回しにしない |

「同じserver・同じtool」は初期の一つの適用範囲にはできるが、それだけでは同じ作用の証明にならない。同じbrowser_clickでも表示更新と削除は異なる。逆に、同じ作業の承認反復を解消するのに少数の別ツールが必要なら、それらを初期の明示ツール群に含める案を検討する。ツール横断の一般化を必須にせず、同じtoolへの限定自体も目的にしない。

初期対象の実作業シナリオはGatewayと選定する。サイト固有の分岐は中核へ追加しない。「対応しやすいツールだけ成功し、困っていた操作は毎回確認のまま」では、その実作業の改善を完了としない。初期対象はまだ未確定であり、本書は特定のブラウザー操作が既に委任可能だと保証するものではない。

## 1. 受け入れる点

SD-01〜08を設計の土台として受け入れる。利用者が確認した具体範囲に対して、独立した判定処理が後続の実callを照合する。単発許可、ツール単位の既存許可、新しい判断委任は別の権限とする。表示だけで委任・禁止ポリシーを有効にしない。

Proxy中核は呼出し対応付け・権限資源・適用競合・上流返信・取消・監査を担当する。候補生成とLLM判断は明示選択する拡張、対象情報の取得は交換可能なadapter、本人確認とUIはGatewayの担当とする。Discord専用の分岐、特定サイト必須、全342ツールの意味解析完了を開始条件にしない。

ただし「全ツールの事前解析不要」と「任意のツールをその場のLLM判断だけで自動許可可能」は同義ではない。自動許可に必要な証拠を取れる操作群・接続先を定義し、その範囲で引数や対象が変わる場合を判定する。未対応箇所は理由と必要な追加機能を明示し、毎回確認するだけで本機能の完成とはしない。

## 2. 合意案へ補完したい事項

### A. 既存の「毎回確認」と「実行禁止」を区別して継承する

既存合意の外部送信・投稿、共有権限変更、削除、任意コード実行、秘密入力・認証操作は、今回の方向性承認だけで自動許可対象へ昇格させない。browser_evaluate、browser_run_code_unsafeも同様。購入など、新しい委任の対象として合意していない作用も自動許可しない。

「毎回確認」は、許可可能な操作を本人がその都度確認すること。「実行禁止」は本人が単発許可しても実行させないこと。優先順位は **禁止 → 必ず個別確認 → 明示された委任の判定 → 単発確認** とする提案。選択されたNotion guardの禁止も維持する。これらの規則は選択した実行に適用し、未選択の標準APIへ新規則を波及させない。

LLMが「閲覧目的」と説明したことだけで、未知のボタンが投稿しないと認定しない。規則の適用に必要な作用を確認できなければ判断不能。対象を広げる場合は、緩和する規則を別途明示合意する。

### B. 利用者が許可する範囲を、表示と保存で一致させる

目的、対象サービス／接続先／アカウント・資源、許容する作用、除外作用、対象ツール群、数量等の制約を一つの版へ束ねる。候補作成に使う利用者の依頼本文・依頼世代も対応付ける。LLMが作った目的を、本人の目的として無条件に採用しない。

「今回のサービス」「関連ページ」だけで許可を取らず、何を指すか本人が確認できる表示を必須にする。対象識別子等の厳密条件と、LLMが判断する自然文条件を分けて保存する。モデルの判断は厳密条件を緩和できない。表示要約にしかない／表示されない裏の条件を作らず、長文は確認済みページへ結び付ける。

UIでは「この範囲を依頼中は許可」の隣に、**確認できる条件はシステムが照合し、意味の判断が必要な場合はAIが判定する**ことを表示する。既存のツール単位許可と両方を同時に出すかはGatewayと別途確定し、同じ名前のボタンへ異なる許可を混在させない。

### C. 対象の証明と、実行まで対象が変わらない条件を分ける

実call ID・引数の対応付けは現在のProxyにある。一方、現行の呼出し記録だけでは、DOM要素、選択中タブ、ブラウザーのログイン先などを操作時まで拘束できるとは確認できていない。

対象識別子、ページ／要素の版、必要な画面情報を取れたことと、その版を実際の実行が使用することは別。承認直前にもう一度画面を取得するだけでは、その後の変化を防げない。adapterがどこまで保証し、MCPサーバーや実行経路に版の照合・排他・対象指定の追加が必要かを実証する。

Proxy内の排他だけで、他クライアント・ブラウザー内スクリプトによる変更まで防げるとはしない。安定した資源IDを引数に持つ操作等と、画面の現在状態に依存する操作を分け、後者を前者の成功で受入済みにしない。

### D. 新旧許可の優先順位と認可境界を定義する

1操作に適用する新委任は1件とし、複数範囲を足し合わせない。候補が複数ある場合も「最も広いもの」をLLMに選ばせず、サーバーの固定順序または明示選択で一件へ決める。新委任を取り消した直後に旧turn許可で同じ操作が進むようなUI上の誤解を避けるため、同一Runで新旧の包括許可を混在させない方式を推奨する。単発許可との併用は維持する。

Run・Responseだけでなく、認証されたクライアント、利用者、会話、入力世代、MCP接続先を拘束する。認証主体と自己申告のprincipal_idは同じではない。共通APIキーを持つクライアント間を、文字列のIDだけで隔離できるとは保証しない。信頼する共通主体として扱う範囲か、クライアント別資格情報による認可を必要とする範囲かを契約に明記する。Discord ID／Bot tokenは不要で、安定した不透明な識別子を使う。

### E. delegation_scope_idを第一級の資源として扱う

`delegation_scope_id` は論理項目名の提案であり、APIキー名の最終合意ではない。Proxyが発行する不透明な一意IDとし、以下の認証・実行情報へ不変に対応付ける。単なる文字列連結や、クライアントが自由に申告できるIDの一致を認可の代わりにしない。

- 認証済みクライアントの信頼境界と、そのクライアントが保証する利用者ID。
- 会話／チャンネル／スレッドに相当する不透明ID。
- クライアントの依頼ID、ProxyのResponse／Run ID、入力世代。
- Proxy instance、正式復元の世代、権限が有効な稼働世代。

同じ依頼の通信再送は同じscopeを照会する。別会話・別Run・次の発言・Steer後は旧scopeを使用不可とし、新scopeが必要。新scopeを作っても委任は自動で引き継がない。完了・停止・取消では元scopeまたは対象委任を無効化する。Proxy再起動・正式復元では旧権限を失効し、旧IDは監査・結果照会だけに使用する。承認ボタンの押下とGatewayだけの再起動は新しい利用者指示に数えない。

scope IDだけで全検証を省略しない。同じscope内での個別取消・委任版・モデル／規則変更・call ID・引数・接続先・対象証拠の照合は別に必要。IDを知っていることも認可にはならない。委任範囲の版や個別判定結果をscope自体と混同しない。

### F. 固定の除外規則を意味判定より先に適用する

初期委任で少なくとも次を毎回確認とする案を、Aの具体化として提示する。

| 個別確認対象 | 判定器への扱い |
| --- | --- |
| 任意コード実行。browser_run_code_unsafe、browser_evaluateを含む | 意味委任の候補生成・範囲内判定には渡さない |
| 認証情報・秘密情報の入力、認証に関する操作 | 秘密値を意味判定器へ送らず、本人向けの個別確認へ |
| 購入確定、投稿・メッセージ・ファイル等の外部送信 | 固定規則に該当した時点で個別確認へ |
| 公開範囲・共有設定・権限の変更、削除 | 固定規則に該当した時点で個別確認へ |

既存guard等で禁止されるものは、個別確認ではなく実行禁止とする。通常の検索・取得が通信を伴うだけで一律に「外部送信」とは分類せず、送信内容・宛先・作用で区別する。秘密の送信や状態変更を通常検索の扱いで許可しない。

固定除外と、その操作が除外に当たるかの証拠は別。管理下のツール識別・照合済み定義・adapterの情報を使用し、実行LLMやツールの自己申告だけでは個別確認対象を解除しない。ツール種別・秘密入力・確定した作用から固定除外に該当するものは、意味委任LLMへ渡さず個別確認または禁止とする。

一方、**対象との対応が取れた証拠はあるが、その操作の作用を解釈する必要がある場合**は、独立LLMの判定対象にできる。事前に全ての作用を機械的に証明することを前提にしない。判定には、除外作用に当たるか、承認範囲に含まれるかを含める。固定規則で既に除外した操作をLLMの肯定で解除することは不可。LLMが投稿・削除等の除外作用と判断した場合も、Proxyが固定規則に従って個別確認へ戻す。作用を判断できない場合も自動許可しない。機械判定できないことと、判断に必要な証拠がないことを区別する。

実callとの対応付け不足、必要な対象情報の欠落・古さ、必要な対象拘束の不成立は、意味解釈では補えない。情報を追加取得するか個別確認とし、対応可能になるための追加機能を示す。全ツールを解析せず、初期対象の操作群についてこの境界を実証する。

### G. LLMを毎回呼ばない判定経路を設ける

候補生成時にLLMを使うことはできるが、LLMが出力した条件をそのまま自動承認プログラムにしない。ポリシー拡張が対応する固定の条件形式へ検証・変換し、表示する自然文範囲と条件の対応を確定させてから本人が承認する。

承認後の各実callは次の順で判定する。

1. 有効scope、委任版、実call・引数・設定・証拠を確認する。
2. 固定の実行禁止／個別確認規則を適用する。
3. 承認された全条件を、照合済みの機械判定ルールと現在の証拠で確定できれば、LLMを呼ばずに許可する。
4. 固定除外に該当することが確定しておらず、実callとの対応・必要な証拠・厳密条件を満たし、作用の分類や承認範囲との照合に意味解釈が必要な場合は、独立したLLMへ判断を求める。除外作用と判断された場合は固定規則へ戻し、LLMが規則自体を緩めることは認めない。
5. 範囲外・判断不能なら人へ確認する。許可直前の再照合、送信意思の保存、取消との競合制御は両経路で共通にする。

厳密条件は接続先・対象資源・作用・引数条件・回数等。条件形式で表せない自然文制約が残っているのに、一部の一致だけで高速経路へ通さない。LLMの肯定結果や単発許可から、新しい機械判定ルールを自動学習・追加しない。

例えば `allowed_effects: [search, sort]` は、利用者が認めた作用を表すだけで、実callがsearchやsortだという証拠ではない。同一ドメインへのbrowser_navigateというだけでも、状態変更URL・別アカウント・リダイレクト等を含む任意操作が範囲内とは言えない。ルールが必要とする対象・作用を確認できる場合に限定する。引数が変わってもこの条件を満たせば許可でき、引数の完全一致だけには戻さない。

LLMを呼ばない経路も監査し、どの条件と証拠で適用したかを保存する。これは古いLLM結論の無条件キャッシュではない。回数・費用・入力世代・取消等の制約を迂回しない。必要な意味判断がある場合は、その経路に対応する判定器が使えることを前提に委任を受け付ける。停止・モデル障害時に高速経路へ勝手に切り替えない。

## 4. 判定器の位置付け

機械的検証は、範囲ID・call対応付け・版・証拠参照・構造化応答などの整合を保証する。結論の意味的な正しさまで保証するものではない。同一モデルの別会話でも誤りが独立するとは限らない。

ページ・ツール定義・取得資料・実行LLMの説明を、判定器への信頼された命令へ昇格させない。判定器に承認を書き込む資格情報や操作用ツールを与えない。不正応答・曖昧な対象・証拠なしの結論は判断不能にする。判定結果をキャッシュする場合も引数だけでなく、委任版・対象証拠・入力世代・モデル／規則版を拘束し、初期版での積極的な判定再利用は必須としない。

監査には結論・短い根拠・版・証拠参照・送信状態を保存し、内部思考を保存しない。目的や対象、短い根拠自体にも個人情報があり得るため、監査は一律公開せず認可・保持・削除を設計する。判定モデルへ送る内容と、Discordで公開できる内容は別の判定とする。

## 5. 実証・受入へ進む順序

1. 本回答0節・A〜G、P-01〜07の推奨をGatewayと照合する。規則の緩和、認証・モデル接続先の追加が必要になった場合は、理由と選択肢を利用者へ提示してから決定する。
2. 実証用の手順・データ範囲・成功／不合格条件を文書化する。常駐の自動許可や実サービスの更新・投稿は行わず、隔離した読み取り・判定のみで実現性を調べる。これは製品実装を先行する許可ではない。
3. S-A01〜12へ次を追加して双方で合意する：既存個別確認規則の維持、新旧許可の混在、別クライアントの認可、判定器の秘密情報受領・操作権限の隔離、対象差替え、モデル／プロンプト変更、人間の長時間確認。危険な誤許可と過剰な再確認を別々に集計する。さらに同じ作業の承認回数、LLM判定回数、機械判定の適用率、判定追加時間（中央値・p95）、作業完了時間、判定費用を前後比較する。初期対象シナリオと改善の合格値を実証前に決め、全体の速度低下を承認回数減少だけで合格にしない。
4. 試験集合と評価条件を実証前に固定する。固定規則違反・別Run適用・送信の重複は一件でも不合格。意味判断の肯定／紛らわしい否定／攻撃入力については、分類ごとの基準を双方で先に決める。有限の試験で誤判定ゼロを証明したとは言わない。
5. 実測を根拠に対応範囲、期限・容量・費用、保持、新APIの全応答例・状態遷移を完成させる。双方の接続レビューと内部設計が完了してから製品コードに着手する。

実現困難な操作では「個別確認で使える」ことと「この機能で委任できる」ことを明確に分ける。必要な対象指定／版照合機能が上流にないなら、必要な上流拡張・adapter経由の実行などの代案と適用範囲を提示し、利用者が求める連続操作の実用性を確認する。全ツールの解析完了待ちには戻さない。

## 6. Gatewayへ返す要旨

方向性は基本合意です。最上位目的を「同一依頼中の繰り返し承認を減らし、待ち時間も減らす」に固定し、初期の対応範囲と将来の拡張範囲を分けます。scope IDの発行・失効、意味判定へ渡さない固定除外、機械的に照合できる操作はLLMを呼ばない経路を追加提案します。ただし同じtoolだけで同じ作用とは判断せず、独立判定・必要な対象証拠と拘束・取消・復旧・永続監査は初期対応範囲でも必須です。実際に困っている連続作業を受入シナリオに選び、承認回数・待ち時間・費用の改善を測定します。具体契約と内部設計の合意前に、製品コード・常駐設定は変更しません。
